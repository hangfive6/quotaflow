# QuotaFlow 中文面试手册

这份手册的目标是：不背术语，真正理解项目。面试时只讲自己能解释、能在代码中指出的位置。

## 一句话介绍

QuotaFlow 是一个库存预占服务。用户下单时先临时锁住库存，在 15 分钟内确认就完成预占，取消或超时则自动返还库存；系统同时处理重复请求和多人抢同一库存的问题。

## 30 秒项目介绍

> 我做的是一个单体 Spring Boot 库存预占服务，适用于限量商品或活动名额。核心流程包括创建库存、预占、确认、取消和超时释放。我重点处理了两个实际问题：第一，用带库存条件的 update SQL 原子扣减，避免并发超卖；第二，通过幂等键和数据库唯一索引避免重复请求导致重复扣库存。项目使用 MySQL、JPA 和 Flyway，提供 Swagger、统一异常、并发测试和 Docker 部署。

这段已经足够用于大多数项目开场。面试官继续追问时再展开，不要主动堆概念。

## 两分钟业务流程

1. 管理端创建一个库存为 100 的商品。
2. 客户端请求预占 1 件，并携带唯一的 `X-Idempotency-Key`。
3. 服务先检查这个幂等键是否已经成功处理；处理过就返回原记录。
4. 服务执行一条条件更新 SQL。库存足够才扣减，受影响行数为 0 代表库存不足。
5. 扣减成功后写入一条 `PENDING` 预占单，默认 15 分钟过期。
6. 用户支付成功后把预占单改为 `CONFIRMED`；主动取消则改为 `CANCELLED` 并返还库存。
7. 定时任务扫描超时的 `PENDING` 记录，改为 `EXPIRED` 并返还库存。

## 必须真正掌握的三个点

### 1. 为什么不会超卖？

错误做法是先查询库存，再在 Java 中判断，最后更新。两个线程可能都读到库存为 1，然后都扣减成功。

本项目把判断和扣减合成同一条 SQL：

```sql
UPDATE products
SET available_stock = available_stock - :quantity
WHERE id = :id AND available_stock >= :quantity;
```

数据库对单条更新保证原子性。第一个事务扣完后，第二个事务再次判断 `available_stock >= quantity` 时不成立，因此影响 0 行。服务根据影响行数返回“库存不足”。

### 2. 为什么幂等要“查询 + 唯一索引”？

查询是为了快速返回已经存在的结果，但仅查询不够。两个相同请求可能同时查询，都发现记录不存在。数据库的 `idempotency_key` 唯一索引是最后防线，保证最终只有一条记录能够插入。

如果竞争失败的事务已经扣过库存，整个方法上的 `@Transactional` 会回滚本事务，扣减也随之回滚，不会少库存。

### 3. 为什么取消和过期要加行锁？

取消请求与过期任务可能同时处理同一条预占单。如果都读到 `PENDING` 并各自返还一次，就会多加库存。`findByIdForUpdate` 使用悲观写锁，让同一时刻只有一个事务能够改变这条预占单。后进入的事务会看到更新后的状态，不再重复返还。

## 高频问题与回答

### Q1：为什么选择单体，不做微服务？

项目业务边界小，单体开发和部署成本更低，事务也更简单。中小业务应先保证正确性和交付速度。当商品、订单、营销由不同团队维护且需要独立扩缩容时，再按业务边界拆分。

### Q2：为什么不用 Redis 分布式锁？

当前规模下数据库就是库存事实来源，条件更新简单可靠，不需要额外维护 Redis 和锁的过期、续期、一致性问题。流量明显超过数据库承载能力时，才考虑 Redis Lua 预扣加消息队列异步落库。

### Q3：`@Transactional` 在这里做了什么？

它让库存扣减、预占单写入和事件记录处于同一个事务。中间任何一步抛出运行时异常，前面的数据库修改都会回滚，避免只扣库存但没有预占单。

### Q4：为什么不能只在 Java 里判断库存？

Java 判断基于一次旧快照，检查和更新之间存在时间窗口。并发线程可能通过同一次判断。把条件放进 update SQL 才能让数据库在更新瞬间判断。

### Q5：幂等键由谁生成？

通常由调用方按一次业务操作生成，例如订单号或 UUID。重试必须使用同一个键；新业务操作必须使用新键。实际系统还会把用户或租户加入唯一范围，避免不同用户的键冲突。

### Q6：为什么预占单需要四个状态？

`PENDING` 表示库存已锁定但业务未完成；`CONFIRMED` 表示已确认；`CANCELLED` 表示用户主动取消；`EXPIRED` 表示超时自动释放。明确状态能限制非法操作并方便审计。

### Q7：确认时发现已经过期怎么办？

服务拒绝确认并返回 `INVALID_STATE`。库存最终由过期任务释放。生产系统可以在确认事务中同步执行过期处理，进一步减少定时任务尚未扫描时的短暂等待。

### Q8：定时任务多实例部署会重复释放吗？

当前通过数据库行锁保护同一条记录，拿到锁后的事务会再次依据状态处理，因此不会重复释放。但扫描大量数据时应分页，并可使用 ShedLock、任务分片或 `SKIP LOCKED` 提升多实例效率。

### Q9：为什么用 Flyway？

Flyway 把建表和变更脚本纳入版本管理。新环境启动时按顺序执行，避免开发、测试、生产数据库结构不一致，也能在代码审查中看到表结构变化。

### Q10：H2 和 MySQL 各自做什么？

H2 让面试官或开发者无需安装数据库就能快速运行项目；MySQL 是实际部署配置。H2 不能完全替代 MySQL 行为验证，生产项目应再用 Testcontainers 跑 MySQL 集成测试。

### Q11：并发测试如何工作？

测试创建 10 件库存，使用 30 个线程通过两个 `CountDownLatch` 同时发起预占。最后断言成功数只能是 10，剩余库存必须是 0。它验证核心规则，而不是追求压测吞吐量。

### Q12：限流实现有什么缺点？

示例限流保存在单机内存中，只适合演示和单实例保护；多实例之间不共享，而且客户端集合需要定期清理。生产环境应使用网关限流或 Redis，并按用户、接口和业务成本设计规则。

### Q13：Outbox 是什么？

它是在业务事务内同时写一条待发布事件，后台任务再发布。这样不会出现业务已提交但消息没发送的问题。当前项目用日志模拟发布，没有声称接入 Kafka。发布可能重复，所以真实消费者仍需幂等。

### Q14：最重要的数据库索引有哪些？

`idempotency_key` 唯一索引用于幂等兜底；`(status, expires_at)` 联合索引用于快速扫描待过期记录；Outbox 的 `(published_at, created_at)` 用于查找未发布事件。

### Q15：项目还有什么不足？

没有登录鉴权、分页、真实消息队列、MySQL Testcontainers 和压测报告；内存限流不支持多实例。回答不足不是扣分，关键是说明当前边界和合理演进方向。

## 现场演示顺序

1. 启动：`mvn spring-boot:run`。
2. 打开 `/swagger-ui.html`，创建库存为 2 的商品。
3. 用同一个幂等键请求两次，说明返回的是同一预占单且只扣一次。
4. 换新幂等键继续预占，直到返回 `INSUFFICIENT_STOCK`。
5. 取消一个预占，再查询商品，展示库存已返还。
6. 执行 `mvn test`，展示并发测试通过。

## 简历表述边界

可以说：独立完成、并发防超卖、接口幂等、事务、行锁、定时释放、Flyway、并发测试、Docker。

不要说：百万 QPS、生产落地、接入 Kafka、Redis 分布式锁、微服务治理。项目没有实现这些内容，被追问很容易露馅。

## 最后自测

如果你能不看文档回答下面五题，就已经能稳定应对多数中小厂面试：

1. 一个预占请求从 Controller 到数据库经历了什么？
2. 两个线程抢最后一件库存时，数据库发生了什么？
3. 两个完全相同的请求同时到达时，为什么只会成功一次？
4. 取消和过期同时发生时，为什么库存不会返还两次？
5. 如果访问量增长 100 倍，你会先观察什么，再改什么？
